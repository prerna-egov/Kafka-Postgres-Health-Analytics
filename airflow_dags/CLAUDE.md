# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository status

This is an early-stage data engineering repository, mostly SQL DDL plus a small but growing set of Airflow DAGs (no build system, linter, or test suite yet). Two DAGs run the pipeline: `airflow_dags/dags/raw_event_to_bronze_orchestrator.py` (raw events → bronze) and `airflow_dags/dags/sql_based_dags/bronze_to_silver_task_orchestrator.py` (bronze → silver), which runs each of the 22 entities' transformations (`airflow_dags/dags/sql_based_dags/<entity>_transformation.py`) as one of its own tasks (see [Bronze → silver orchestration](#bronze--silver-orchestration) below). On the `ddl/` (Postgres) side, `02_data_marts.sql` is still an empty placeholder. The ClickHouse side is fully populated: `04_bronze_tables.sql` has real `stg_*` bronze table definitions for the entities these DAGs read from, and `07_mart_tables.sql` / `08_coverage_marts.sql` hold the first gold-layer marts.

Because there is no build/lint/test tooling yet, do not invent commands for these — verify SQL by inspection against the pipeline stage it belongs to (see below), and note explicitly to the user when a stage is unimplemented rather than filling it in speculatively.

## Repository layout

- `ClickHouse_ddl/` — DDL for the ClickHouse side of the pipeline (Kafka table engine, raw event store, bronze/silver tables, dimension tables, coverage marts).
- `ddl/` — DDL for the downstream analytics Postgres side (enriched/transformed tables consumed by reporting, and data marts).
- `airflow_dags/` — Airflow DAGs orchestrating movement of data between the ClickHouse stages.

## Data architecture (Postgres CDC → Kafka → ClickHouse → Postgres analytics)

This pipeline captures change-data-capture (CDC) events from the operational Postgres database behind eGov DIGIT Health Campaign Management (HCM) services and makes them analytics-ready for reporting. The core domain entities are household, household member, project, project task, project beneficiary, project staff, PGR complaints, attendance (log/register), and stock/stock reconciliation. The flow is:

1. **Source Postgres (operational DB, outside this repo)** — the live DIGIT service database that HCM applications write to.
2. **Debezium** — captures write-ahead log changes from the source Postgres tables and publishes them as change events to Kafka topics (one topic per source table/entity, e.g. `save-household-events`).
3. **Kafka table engine (`ClickHouse_ddl/01_kafka_event_consumers.sql`)** — ClickHouse `Kafka` engine tables consume each topic and store each message as a raw JSON string. These are not queried directly; they only exist to bridge Kafka into ClickHouse.
4. **Materialized view → raw event store (`ClickHouse_ddl/02_raw_events_store.sql`, `ClickHouse_ddl/03_raw_events_ingestion_mvs.sql`)** — `02` defines the `<entity>_events_raw` store tables, `03` the `mv_<entity>_events_raw` materialized views that sit on top of each Kafka engine table and insert into them, giving a persisted, replayable log of every CDC event.
5. **Bronze tables (`ClickHouse_ddl/04_bronze_tables.sql`)** — intended to be populated by an Airflow DAG that reads from the raw event store and writes into bronze tables, which are structural replicas of the source Postgres tables (`stg_<entity>`, pre-transformation, one-to-one with the operational schema, plus an `_ingested_at` arrival-time column). The table definitions themselves already exist; the raw-event-store-to-bronze *loading* DAG does not (see step 10) — today, bronze data is assumed to already be present when a `<entity>_transformation.py` DAG runs.
6. **Silver tables (`ClickHouse_ddl/05_silver_tables.sql`)** — populated by `bronze_to_silver_task_orchestrator`, which runs each entity's transformation (`dags/sql_based_dags/<entity>_transformation.py`) as a task (see below); each reads from bronze, apply transformations (flattening nested fields, joining in boundary hierarchy and campaign/project context, etc.), and write fully flattened, analytics-ready tables per entity (`household_entity`, `household_member_entity`, `project_beneficiary_entity`, `pgr_complaints_entity`, `project_staff_entity`, `stock_entity`, `service_task_entity`, `stock_reconciliation_entity`, `project_entity`, `project_task_entity`). All use `ReplacingMergeTree` keyed on a modification timestamp column (dedup-on-merge semantics), `ORDER BY` tuples starting with tenant/campaign identifiers for query locality, and secondary `set()`/`minmax` data-skipping indexes on geography and date columns for fast filtering at scale. `project_task_transformation.py`, `project_transformation.py`, `project_staff_transformation.py`, `project_beneficiary_transformation.py`, `household_transformation.py`, `household_member_transformation.py`, `stock_transformation.py`, `pgr_transformation.py`, `stock_reconciliation_transformation.py`, `attendance_staff_transformation.py`, `attendance_register_transformation.py`, `attendee_transformation.py`, `attendance_log_transformation.py`, `bill_transformation.py`, `bill_detail_transformation.py`, `referral_transformation.py`, `side_effect_transformation.py`, `hf_referral_transformation.py`, `user_action_transformation.py`, `service_task_transformation.py`, and `muster_roll_transformation.py` (plus `device_token_transformation.py`) are the entities with real transform logic today: each reads bronze, joins in related bronze tables, enriches rows with boundary/user/product/individual/facility data as applicable (see [Shared helper modules](#shared-helper-modules)), and writes slice-by-slice into its silver table (`project_task_entity`, `project_entity`, `project_staff_entity`, `project_beneficiary_entity`, `household_entity`, `household_member_entity`, `stock_entity`, `pgr_complaints_entity`, `stock_reconciliation_entity`, `attendance_staff_entity`, `attendance_register_entity`, `attendee_entity`, `attendance_log_entity`, `bill_entity`, `bill_detail_entity`, `referral_entity`, `side_effect_entity`, `hf_referral_entity`, `user_action_entity`, `service_task_entity`, `muster_roll_entity` respectively).
7. **Dimension tables (`ClickHouse_ddl/06_dimension_tables.sql`)** — supporting dimensions, e.g. `boundary_hierarchy_dim`, which unfurls a hierarchical boundary definition (country → region → district → facility → settlement, encoded as `level_one_code` … `level_nine_code` elsewhere) into one row per level.
8. **Coverage marts (`ClickHouse_ddl/07_mart_tables.sql`, `ClickHouse_ddl/08_coverage_marts.sql`)** — the gold layer, aggregating silver into campaign KPIs (`dm_successful_deliveries_base`, `dm_targets_base`, `dm_campaign_coverage`), plus the node-based campaign target model (`dm_campaign_hierarchy`, `dm_campaign`, `dm_campaign_target_fact`, `dm_coverage_by_node`) that makes target roll-ups independent of how deep a campaign's boundary hierarchy happens to be. Storage and logic are split: `07` holds the `MergeTree` target tables, `08` the refreshable materialized views (`mv_dm_*`, `REFRESH EVERY 80 YEAR TO <table>`) that fully rebuild them — create `07` first — no Airflow DAG drives this layer, and the MVs only rebuild on a manual `SYSTEM REFRESH VIEW` (run them one at a time, dependencies first; an hourly schedule got the ClickHouse pod evicted). Every read of a silver table here uses `FINAL`, since silver is `ReplacingMergeTree` and un-merged CDC row versions would otherwise be double-counted.
9. **Downstream analytics Postgres (`ddl/01_transformed_data_tables.sql`, `ddl/02_data_marts.sql`)** — a separate, reporting-facing Postgres database (distinct from the source operational Postgres in step 1) holding enriched tables (`household_enriched`, `household_member_enriched`, `project_beneficiary_enriched`, `attendance_log_enriched`, `attendance_register_enriched`, `pgr_complaints_enriched`) and data marts. These favor `JSONB` for nested/variable structures (`additional_details`, `boundary_hierarchy`, etc.) where the ClickHouse silver tables instead flatten the same data into typed columns — keep this asymmetry in mind when writing transformation logic between the two. `02_data_marts.sql` is an empty placeholder; how silver data reaches this Postgres is not yet defined in this repo — do not assume a mechanism, ask if it's unclear.
10. **Orchestration (`airflow_dags/dags/`)** — Airflow DAGs drive steps 5 and 6: `raw_event_to_bronze` (raw → bronze, one mapped task per table) and `bronze_to_silver_task_orchestrator` (bronze → silver, one task per entity). Both are hourly by default.

## Bronze → silver orchestration

`bronze_to_silver_task_orchestrator` (`dags/sql_based_dags/bronze_to_silver_task_orchestrator.py`) is the only DAG that writes silver. It does no transformation itself: each entity's logic lives in its own file (`dags/sql_based_dags/<entity>_transformation.py`, an `EntitySpec`), so one entity can change without touching the others, and the orchestrator runs it as a task of its own DAG. On each run (hourly by default, `task_orchestrator_schedule`):

1. `resolve_time_window` computes the window: `start_time`/`end_time` from `dag_run.conf`; else, only on a manual/backfill run or an `@once` schedule, `bronze_to_silver_window_start_override`/`_end_override` if both are set; else this run's `data_interval_start`/`data_interval_end` (a real `[previous tick, this tick)` window — `_resolve_schedule` wraps cron/preset schedules in a `CronDataIntervalTimetable`, because Airflow's default `CronTriggerTimetable` gives a zero-width interval). A recurring scheduled run never reads the overrides, so a forgotten override can't freeze later runs; a zero-width window fails loudly.
2. One `transform_<entity>` task per entity in `task_orchestrator_entity_order` (default: every entity module in the folder; any number) calls `sql_flatten_common.run_transformation(SPEC, window)` directly — no other DAG is triggered. Up to `task_orchestrator_max_active_tasks` (default 3) run at once, started in list order (descending `priority_weight`); entities share no tables, so overlap is safe and the limit is ClickHouse CPU.
3. One entity failing never stops the others; `all_entities_succeeded` marks the run failed if any did. Inside an entity, a failed slice is retried once immediately, the remaining slices still run, then the task fails listing the failed slices and Airflow retries it `task_orchestrator_task_retries` times (default 1) — except when every failure was a size guard (`AirflowFailException`, no retry). Each task has a time limit, `task_orchestrator_task_timeout_minutes` (default 120).

Each entity file also registers a standalone `<entity>_transformation` DAG (built by `build_sql_dag`, same `run_transformation` path) for running one entity by hand with a `{start_time, end_time}` conf; nothing schedules or triggers it. These are the **production writers of every silver table**: they keep the eGov service calls in Python but do the flatten + write as ClickHouse `INSERT … SELECT` per slice into the main silver table (and its `<entity>_campaign_field` child table, where one exists), in the ClickHouse connection's own database; `truncate_target` is refused. The original Python DAGs and the old trigger-based `bronze-to-silver_orcestrator.py` are kept for reference only in `airflow_dags/python_reference/` (outside `dags/`, never loaded by Airflow, and no longer matching the silver DDL) — don't extend them, and don't describe the pipeline in their terms (no "triggers each entity's DAG", no chunks); new transformation work goes into `sql_based_dags/`. The entity files share `dags/sql_based_dags/sql_flatten_common.py` (slicing, API lookups as inline VALUES tables, the INSERT rendering, the DAG factory); an entity file declares only its joins, helper expressions and `(silver column, expression)` pairs. Their window reads and join sides rely on the projections in `ClickHouse_ddl/14_bronze_projections.sql` (all of them are in that one file; a query with FINAL never uses a projection, so those sides are argMax subqueries -- extend the projection before reading a new column through it). Airflow's safe-mode discovery needs the words `airflow` and `dag` in a DAG file; the entity files carry them in a comment above `dag = build_sql_dag(SPEC)`. When adding a new entity, follow an existing `sql_based_dags/<entity>_transformation.py` (an `EntitySpec` built with `build_sql_dag`) rather than inventing a new structure; the orchestrator picks the new file up automatically (or add it to `task_orchestrator_entity_order` if that Variable is set).

## Deployment configuration

What a deployment must define is listed, with what each setting does, in [README → First-time setup](README.md#first-time-setup-what-you-must-configure). The split is by mechanism:

- **Helm chart** (the Airflow chart's `.Values.env`, which also reaches KubernetesExecutor worker pods): only settings the code reads with `os.getenv` -- the eGov service hosts `EGOV_BOUNDARY_SERVICE_BASE_URL` (boundary level columns), `EGOV_USER_SERVICE_BASE_URL` (user name/role/address columns), `EGOV_MDMS_SERVICE_BASE_URL` (role choice for multi-role users) and `EGOV_WORKFLOW_SERVICE_BASE_URL` (bill workflow status). The `EGOV_*_PATH` vars have working defaults.
- **Airflow UI**: the Connection `clickhouse_default` (the ClickHouse every DAG uses; its schema is the database silver is written to) and the pool `clickhouse_bronze_extraction` (5 slots, raw→bronze). Variables are all optional with working defaults: `raw_to_bronze_schedule`, `task_orchestrator_schedule` (`@hourly`), `task_orchestrator_entity_order` (all entities), `task_orchestrator_max_active_tasks` (3), `task_orchestrator_task_retries` (1), `task_orchestrator_task_timeout_minutes` (120), `bronze_to_silver_chunk_size` (5000) and the `bronze_to_silver_window_start_override`/`_end_override` pair for reprocessing a past window.
- **Never** put `AIRFLOW_VAR_*` / `AIRFLOW_CONN_*` env vars in the Helm chart: Airflow resolves env vars before the metadata DB, so they silently override the UI and UI edits appear to save but do nothing.

When code adds a new Airflow Variable, Connection, pool or env var, add it to the README's first-time setup section (required or optional, its default, and what it does for the person setting it up) in the same change.

## Shared helper modules

Two plain (non-DAG) helper modules live in `airflow_dags/dags/`:

- **`clickhouse_utils.py`** — `get_clickhouse_client()`, building a `clickhouse-connect` client from the `clickhouse_default` Airflow Connection (see [README](README.md#connecting-the-dags-to-clickhouse)).
- **`egov_api_utils.py`** — calls to external eGov DIGIT services (boundary-service, user-service, MDMS, workflow-service), each following the same simplified-vs-Java approach: read the reference Java `transformer` service (in the sibling `health-campaign-services` repo) to understand the real request/response shape, then reimplement only what's actually needed, dropping incidental complexity the Java code carries (MDMS-based display-name/label resolution, localization-service calls) when the same data is already available more directly (e.g. a boundary code's ancestor path is fetched directly via the boundary-service's `codes=` filter, not derived from an MDMS-labeled whole-tree walk; a project's `beneficiaryType` is read straight out of its own `additional_details` JSON instead of an MDMS `PROJECT_TYPES`-master lookup). Every external call degrades gracefully — wrapped in try/except, logs and returns an empty/default result on any failure, never failing the task. The entity files use it through the lookups in `sql_flatten_common.py` (`boundary_lookup`, `user_lookup`, `workflow_lookup`): per slice, a ClickHouse query returns the slice's distinct keys, `resolve_boundary_levels` / `resolve_user_info` / `resolve_workflow_summaries` resolve them (batched, cached per task), and the results are joined into the slice's single `INSERT … SELECT` as an inline VALUES table. A new entity that needs this enrichment declares one of these lookups rather than calling the services itself.

## Conventions to follow when extending the schema

- **Boundary hierarchy flattening**: entities that are geography-aware repeat the same `level_one_code` … `level_nine_code` + `hierarchy_type` column block (see any table in `05_silver_tables.sql`). Match this exact naming/ordering when adding new entities rather than inventing a new representation.
- **Roll-up cut for hierarchical targets**: a campaign creates one project per boundary, so targets exist at *every* level of its tree and `SUM()` over them double-counts by roughly the tree depth. Any mart that totals targets must first take exactly one cut — `is_campaign_root` or `is_campaign_leaf` on `dm_campaign_hierarchy` — and must never infer "the lowest level" from a hardcoded level column. Boundary depth is chosen per campaign/`hierarchy_type` and varies (1, 3 and 6 all occur in `table_dumps/project_dump_1.csv`); read a campaign's real depth from `dm_campaign.root_level`/`max_level`/`levels_present`. The cautionary example is the `level_nine_code != ''` predicate this replaced: because the `level_*_code` block is left-packed from the root, it matched *only* paths exactly 9 deep, so every real campaign produced zero target rows and zero coverage. Note also that the root/leaf flags must be computed from **ancestor**-set membership, not immediate-parent membership — on a ragged tree (nodes at `M1` and `M1/M2/M3` but not `M2`) the immediate-parent version marks both nodes as root *and* both as leaf, and both cuts double-count. Finally, cut a single `target_type`'s total with `is_target_type_root`/`is_target_type_leaf` on the **fact**, not with the dim's flags: the dim's are computed over the union of all target types' nodes, and a campaign's HOUSEHOLD node set is usually a strict subset of its INDIVIDUAL one (218 of 302 projects in `table_dumps/project_target.csv` carry INDIVIDUAL only), so the union flag silently returns 0 for any type whose nodes exclude the union root.
- **Campaign/project context columns**: most silver entities repeat `project_id`, `project_type`, `project_type_id`, `project_name`, `campaign_number`, `campaign_id` as trailing "EXTRA FIELDS USED BY TRANSFORMER" — carry these through for any new entity so campaign-level rollups keep working.
- **ClickHouse table engine choice**: mart (`dm_*`) tables use plain `MergeTree` — they are rebuilt wholesale by their refreshable MV, so there is nothing to dedupe. Silver/dimension tables use `ReplacingMergeTree(<last_modified_or_created_time_column>)` so late-arriving updates from Kafka dedupe correctly; pick the column that reflects the entity's true last-write time (server `last_modified_time`/`created_time`, or client `client_last_modified_time` when the entity has separate client/server audit trails).
- **Campaign-specific fields live in child tables, not silver**: values that only some campaigns use (every `additionalFields` key, plus derived keys such as `cycleIndex`/`doseIndex`/`isVulnerable`, and project_task's beneficiary details: `age`/`gender`/`dateOfBirth`/`individualId` for individual projects, `householdId`/`memberCount` for household ones) go into `<entity>_campaign_field` (`05_silver_tables.sql`, right after the parent): one row per `(id, key)` with the value TYPED into exactly one of `value_string` / `value_number` (Float64) / `value_date` (Date32) / `value_bool` / `value_array` (Array(String)), named by `value_type`, the other four sent as NULL (`value_array`: `[]`, an Array can't be Nullable) so they take their DDL `DEFAULT` (`'NOT_APPLICABLE'`, `0`, `1970-01-01`, `false`, `[]`; relies on `insert_null_as_default`, pinned in `CLICKHOUSE_INSERT_SETTINGS`) so non-technical users never cast — typed per value by one generic rule in `campaign_field_rows_sql` (true/false → bool; any valid JSON array, or a string holding one → array, one text per element: strings unquoted, numbers/bools/objects as their JSON text; plain number without a leading zero, integers ≤ 15 digits → number; a real `YYYY-MM-DD` → date; everything else, incl. zero-padded text like `"03"`, datetime text, JSON objects and invalid `[` text → string; epoch-ms stays a number), so a key can carry different types on different rows. `ReplacingMergeTree(last_modified_time)` holding the parent's version value, `ORDER BY (id, key)` — one child table per entity, never a shared one. Exists for project_task, household, household_member (its own + individual keys only; household keys are in `household_campaign_field`), project_beneficiary and stock; written by those entities' DAGs in `sql_based_dags/`, and the ONLY place these values are stored: the silver tables carry no derived `additional_details` blob (household, household_member, project_beneficiary, stock), no task `cycleIndex`/`doseIndex`/`delivery_strategy`/`age`/`gender`/`date_of_birth` and no stock `facility_target` (dropped at cutover). The raw bronze blobs stay as silver columns (`household_additional_fields`, `member_additional_fields`, `beneficiary_additional_fields`, stock `additional_fields`, and project_task's `additional_details`, which is the raw `stg_project_task.additional_details`), as do task `individual_id`/`household_id`/`member_count`. To give an entity a child table, set `campaign_fields=campaign_field_rows_sql(<pairs helper>)` and `campaign_version_column` on its `SilverTarget`: the slice is then computed once into a session `TEMPORARY TABLE … ENGINE = Memory` and both the silver row and its child rows are inserted from it (no second pass over bronze, no materialized views). Keys are passed through generically, so a new `additionalDetails` key needs no code or DDL change. A key dropped by a later record version stays behind, so readers join on `child.last_modified_time = parent version`. Marts read these values from the child tables: `mv_dm_smc_administered_base`, `mv_dm_zero_dose_daily_by_node`, `mv_dm_missed_children_daily_by_node` (10) and `mv_dm_stock_facility_points` (11) pivot the child table (`anyIf(value_<type>, key = …)`, cast to the old silver type) joined on the parent's version; follow that pattern in any new mart that needs a campaign value. The custom report SQL in `custom_reports_reference/` still reads the dropped columns and has yet to be ported.
- **Indexing**: add `set(0)` data-skipping indexes on the boundary-code columns used for geographic filtering, and `minmax` indexes on date/timestamp columns queried by range (see `stock_entity`, `project_task_entity` for examples with multiple indexes).
- **Postgres vs. ClickHouse representation**: when adding a Postgres enriched-table counterpart to a ClickHouse silver table, keep nested/variable JSON fields as `JSONB` in Postgres even though the ClickHouse side flattens them into typed columns — do not flatten on the Postgres side unless a specific query pattern requires it.
- Column comments in the DDL (e.g. `-- Household.address (flattened)`) trace fields back to the source DIGIT service's domain object; preserve this traceability when adding columns for a new entity.
- **Bronze read window column**: an entity's bronze window read must filter on the bronze table's own `_ingested_at` column, never on `last_modified_time`. `last_modified_time` reflects when a record changed at the *source* Postgres DB; because of pipeline latency (Debezium → Kafka → raw event store → `raw_event_to_bronze`), a row modified within a given `[start_time, end_time)` window can land in bronze well after that window has already been processed, so filtering on it would silently and permanently miss such late-arriving rows. `_ingested_at` correctly captures "what showed up in bronze during this run," independent of when the source-side edit happened. `last_modified_time` is still the right column for the silver-side `ReplacingMergeTree` versioning — a separate concern. In the SQL DAGs this lives in `sql_flatten_common.py`: `plan_slices` reads `(tenant_id, id)` of the driving table where `_ingested_at` is in the window (one query, served by the table's narrow `prj_ingested_at` projection) and cuts per-tenant id ranges of at most `bronze_to_silver_chunk_size` rows; each slice's statement then selects its rows with the same `_ingested_at` filter inside its id range. Keep that window query to `tenant_id, id, _ingested_at` with no `FINAL`, and extend a projection in `ClickHouse_ddl/14_bronze_projections.sql` before reading a new column through it, or the projection silently becomes ineligible and the full scan returns.
- **No unconditional joins for mutually-exclusive per-row lookups**: when a row's next enrichment step branches on a value already known per row (e.g. a task's `beneficiaryType` is `HOUSEHOLD` *or* `INDIVIDUAL`, never both), don't `LEFT JOIN` a whole branch table onto every row. In the SQL DAGs every join side is filtered to the slice's own keys first (e.g. project_task's household and individual sides are point lookups bounded to the slice's beneficiary refs, through projections), and the branch is chosen per row in the column expressions — see the note at the top of `sql_based_dags/project_task_transformation.py`. A join side that isn't bounded to the slice is the thing to avoid.
