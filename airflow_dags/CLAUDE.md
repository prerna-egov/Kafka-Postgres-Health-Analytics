## Repository layout

- `ClickHouse_ddl/` — DDL for the ClickHouse side of the pipeline (Kafka table engine, raw event store, bronze/silver tables, dimension tables, coverage marts).
- `ddl/` — DDL for the downstream analytics Postgres side (enriched/transformed tables consumed by reporting, and data marts).
- `airflow_dags/` — Airflow DAGs orchestrating movement of data between the ClickHouse stages.

## Data architecture (Postgres CDC → Kafka → ClickHouse → Postgres analytics)

This pipeline captures change-data-capture (CDC) events from the operational Postgres database behind eGov DIGIT Health Campaign Management (HCM) services and makes them analytics-ready for reporting. The core domain entities are household, household member, project, project task, project beneficiary, project staff, PGR complaints, attendance (log/register), and stock/stock reconciliation. The flow is:

1. **Source Postgres (operational DB, outside this repo)** — the live DIGIT service database that HCM applications write to.
2. **Debezium** — captures write-ahead log changes from the source Postgres tables and publishes them as change events to Kafka topics (one topic per source table/entity, e.g. `save-household-events`).
3. **Kafka table engine (`ClickHouse_ddl/01_kafka_event_consumers.sql`)** — ClickHouse `Kafka` engine tables consume each topic and store each message as a raw JSON string. These are not queried directly; they only exist to bridge Kafka into ClickHouse.
4. **Materialized view → raw event store (`ClickHouse_ddl/02_raw_events_store.sql`, `ClickHouse_ddl/03_raw_events_ingestion_mvs.sql`)** — `02` defines the `<entity>_events_raw` store tables, `03` the `mv_<entity>_events_raw` materialized views that sit on top of each Kafka engine table and insert into them, giving a persisted, replayable log of every CDC event.
5. **Bronze tables (`ClickHouse_ddl/04_bronze_tables.sql`)** — intended to be populated by an Airflow DAG that reads from the raw event store and writes into bronze tables, which are structural replicas of the source Postgres tables (`stg_<entity>`, pre-transformation, one-to-one with the operational schema, plus an `_ingested_at` arrival-time column). The table definitions themselves already exist; the raw-event-store-to-bronze *loading* DAG does not (see step 10) — today, bronze data is assumed to already be present when a `<entity>_transformation.py` DAG runs.
6. **Silver tables (`ClickHouse_ddl/05_silver_tables.sql`)** — populated by the per-entity transformation DAGs in `dags/sql_based_dags/` that `bronze-to-silver_orcestrator.py` triggers (see below), which read from bronze, apply transformations (flattening nested fields, joining in boundary hierarchy and campaign/project context, etc.), and write fully flattened, analytics-ready tables per entity (`household_entity`, `household_member_entity`, `project_beneficiary_entity`, `pgr_complaints_entity`, `project_staff_entity`, `stock_entity`, `service_task_entity`, `stock_reconciliation_entity`, `project_entity`, `project_task_entity`). All use `ReplacingMergeTree` keyed on a modification timestamp column (dedup-on-merge semantics), `ORDER BY` tuples starting with tenant/campaign identifiers for query locality, and secondary `set()`/`minmax` data-skipping indexes on geography and date columns for fast filtering at scale. `project_task_transformation.py`, `project_transformation.py`, `project_staff_transformation.py`, `project_beneficiary_transformation.py`, `household_transformation.py`, `household_member_transformation.py`, `stock_transformation.py`, `pgr_transformation.py`, `stock_reconciliation_transformation.py`, `attendance_staff_transformation.py`, `attendance_register_transformation.py`, `attendee_transformation.py`, `attendance_log_transformation.py`, `bill_transformation.py`, `bill_detail_transformation.py`, `referral_transformation.py`, `side_effect_transformation.py`, `hf_referral_transformation.py`, `user_action_transformation.py`, `service_task_transformation.py`, and `muster_roll_transformation.py` (plus `device_token_transformation.py`) are the entities with real transform logic today: each reads bronze, joins in related bronze tables, enriches rows with boundary/user/product/individual/facility data as applicable (see [Shared helper modules](#shared-helper-modules)), and writes slice-by-slice into its silver table (`project_task_entity`, `project_entity`, `project_staff_entity`, `project_beneficiary_entity`, `household_entity`, `household_member_entity`, `stock_entity`, `pgr_complaints_entity`, `stock_reconciliation_entity`, `attendance_staff_entity`, `attendance_register_entity`, `attendee_entity`, `attendance_log_entity`, `bill_entity`, `bill_detail_entity`, `referral_entity`, `side_effect_entity`, `hf_referral_entity`, `user_action_entity`, `service_task_entity`, `muster_roll_entity` respectively).
7. **Dimension tables (`ClickHouse_ddl/06_dimension_tables.sql`)** — supporting dimensions, e.g. `boundary_hierarchy_dim`, which unfurls a hierarchical boundary definition (country → region → district → facility → settlement, encoded as `level_one_code` … `level_nine_code` elsewhere) into one row per level.
8. **Coverage marts (`ClickHouse_ddl/07_mart_tables.sql`, `ClickHouse_ddl/08_coverage_marts.sql`)** — the gold layer, aggregating silver into campaign KPIs (`dm_successful_deliveries_base`, `dm_targets_base`, `dm_campaign_coverage`), plus the node-based campaign target model (`dm_campaign_hierarchy`, `dm_campaign`, `dm_campaign_target_fact`, `dm_coverage_by_node`) that makes target roll-ups independent of how deep a campaign's boundary hierarchy happens to be. Storage and logic are split: `07` holds the `MergeTree` target tables, `08` the refreshable materialized views (`mv_dm_*`, `REFRESH EVERY 80 YEAR TO <table>`) that fully rebuild them — create `07` first — no Airflow DAG drives this layer, and the MVs only rebuild on a manual `SYSTEM REFRESH VIEW` (run them one at a time, dependencies first; an hourly schedule got the ClickHouse pod evicted). Every read of a silver table here uses `FINAL`, since silver is `ReplacingMergeTree` and un-merged CDC row versions would otherwise be double-counted.
9. **Downstream analytics Postgres (`ddl/01_transformed_data_tables.sql`, `ddl/02_data_marts.sql`)** — a separate, reporting-facing Postgres database (distinct from the source operational Postgres in step 1) holding enriched tables (`household_enriched`, `household_member_enriched`, `project_beneficiary_enriched`, `attendance_log_enriched`, `attendance_register_enriched`, `pgr_complaints_enriched`) and data marts. These favor `JSONB` for nested/variable structures (`additional_details`, `boundary_hierarchy`, etc.) where the ClickHouse silver tables instead flatten the same data into typed columns — keep this asymmetry in mind when writing transformation logic between the two. `02_data_marts.sql` is an empty placeholder; how silver data reaches this Postgres is not yet defined in this repo — do not assume a mechanism, ask if it's unclear.
10. **Orchestration (`airflow_dags/dags/`)** — Airflow DAGs drive steps 5 and 6 (raw → bronze, and bronze → silver). Only the bronze→silver side exists so far; the raw→bronze DAG does not exist yet.

## Orchestrator DAG and per-entity transformation DAGs

`bronze-to-silver_orcestrator.py` (`dag_id=bronze_to_silver_orchestrator`) does not itself do any bronze→silver work. Each entity gets its own DAG file (`dags/sql_based_dags/<entity>_transformation.py`, `dag_id=<entity>_transformation`, e.g. `project_task_transformation.py`) so that transformation logic for one entity can change without touching the others. The orchestrator, on each scheduled run:

1. Computes a time window: `bronze_to_silver_window_start_override`/`_end_override` (Airflow Variables) if both are set *and* this run is manual/backfill or a one-off `@once` schedule, else falls back to this run's own `data_interval_start`/`data_interval_end` (a real `[previous tick, this tick)` window, e.g. previous hour for `@hourly` — `_resolve_schedule` explicitly wraps cron/preset schedules in a `CronDataIntervalTimetable` for this; Airflow's default string-schedule resolution (`CronTriggerTimetable`) would otherwise give a zero-width `data_interval_start == data_interval_end` on every scheduled run). A normal recurring scheduled run always uses `data_interval_start`/`data_interval_end`, ignoring the override variables even if they're still set, so a forgotten override from a manual backfill can't silently freeze future scheduled runs. If the resolved window is ever zero-width anyway (`"None"`/`"@once"` schedule with no valid override), the task fails loudly instead of silently processing an empty window.
2. Reads the ordered list of entities to process from the `entity_transformation_order` Airflow Variable.
3. For each entity in order, triggers `<entity>_transformation` with `conf={"start_time": ..., "end_time": ...}` and waits for it to finish before triggering the next one. If an entity's DAG file doesn't exist yet, it's skipped (not a hard failure) and the chain continues; a genuine failure in a triggered DAG is logged via that entity's own failed `trigger_<entity>` task but also does not halt the chain — every entity in the order is still attempted, and the orchestrator's own run is still marked failed overall so monitoring/alerting still catches it.

Both the entity order and the orchestrator's own schedule cadence are controlled by Airflow Variables rather than hardcoded, so operators can change them without a code deploy — see [`airflow_dags/README.md`](README.md) for exactly how to set them and what values are valid. The entity DAGs in `airflow_dags/dags/sql_based_dags/` are the **production writers of every silver table**: they keep the eGov service calls in Python but do the flatten + write as ClickHouse `INSERT … SELECT` per slice into the main silver table (and its `<entity>_campaign_field` child table, where one exists), in the ClickHouse connection's own database; `truncate_target` is refused. The original Python DAGs are kept for reference only in `airflow_dags/python_reference/` (outside `dags/`, never loaded by Airflow, and no longer matching the silver DDL) -- don't extend them; new transformation work goes into `sql_based_dags/`. The entity DAGs share `dags/sql_based_dags/sql_flatten_common.py` (slicing, API lookups as inline VALUES tables, the INSERT rendering, the DAG factory); an entity file declares only its joins, helper expressions and `(silver column, expression)` pairs. Their window reads and join sides rely on the projections in `ClickHouse_ddl/14_bronze_projections.sql` (all of them are in that one file; a query with FINAL never uses a projection, so those sides are argMax subqueries -- extend the projection before reading a new column through it). Airflow's safe-mode discovery needs the words `airflow` and `dag` in a DAG file; the entity files carry them in a comment above `dag = build_sql_dag(SPEC)`. When adding a new entity, follow an existing `sql_based_dags/<entity>_transformation.py` (an `EntitySpec` built with `build_sql_dag`) rather than inventing a new structure, and add its key to `entity_transformation_order` once it's ready to run. `bronze_to_silver_task_orchestrator.py` in the same folder runs every entity as a task of one DAG instead (see README).

## Shared helper modules

Two plain (non-DAG) helper modules live in `airflow_dags/dags/` and are reused by the entity DAGs:

- **`clickhouse_utils.py`** — `get_clickhouse_client()`, building a `clickhouse-connect` client from the `clickhouse_default` Airflow Connection (see [README](README.md#connecting-entity-dags-to-clickhouse)).
- **`egov_api_utils.py`** — calls to external eGov DIGIT services (boundary-service, user-service, MDMS), each following the same simplified-vs-Java approach: read the reference Java `transformer` service (in the sibling `health-campaign-services` repo) to understand the real request/response shape, then reimplement only what's actually needed, dropping incidental complexity the Java code carries (MDMS-based display-name/label resolution, localization-service calls) when the same data is already available more directly (e.g. a boundary code's ancestor path is fetched directly via the boundary-service's `codes=` filter, not derived from an MDMS-labeled whole-tree walk; a project's `beneficiaryType` is read straight out of its own `additional_details` JSON instead of an MDMS `PROJECT_TYPES`-master lookup). Every external call degrades gracefully — wrapped in try/except, logs and returns an empty/default result on any failure, never a hard chunk failure. It also hosts an **entity-agnostic three-stage pattern** (`extract_*_lookup_keys` → `resolve_*` → `attach_*`) for enriching a chunk of rows from an external source: an entity file supplies a small `get_key(row)` function mapping its own column names to a generic lookup key, and the reusable functions handle grouping/deduping, batched resolution, and merging results back onto rows. Follow this pattern (rather than inventing a new one) when a new entity needs boundary/user enrichment, or needs a similar kind of external/lookup-table enrichment of its own.

## Conventions to follow when extending the schema

- **Boundary hierarchy flattening**: entities that are geography-aware repeat the same `level_one_code` … `level_nine_code` + `hierarchy_type` column block (see any table in `05_silver_tables.sql`). Match this exact naming/ordering when adding new entities rather than inventing a new representation.
- **Roll-up cut for hierarchical targets**: a campaign creates one project per boundary, so targets exist at *every* level of its tree and `SUM()` over them double-counts by roughly the tree depth. Any mart that totals targets must first take exactly one cut — `is_campaign_root` or `is_campaign_leaf` on `dm_campaign_hierarchy` — and must never infer "the lowest level" from a hardcoded level column. Boundary depth is chosen per campaign/`hierarchy_type` and varies (1, 3 and 6 all occur in `table_dumps/project_dump_1.csv`); read a campaign's real depth from `dm_campaign.root_level`/`max_level`/`levels_present`. The cautionary example is the `level_nine_code != ''` predicate this replaced: because the `level_*_code` block is left-packed from the root, it matched *only* paths exactly 9 deep, so every real campaign produced zero target rows and zero coverage. Note also that the root/leaf flags must be computed from **ancestor**-set membership, not immediate-parent membership — on a ragged tree (nodes at `M1` and `M1/M2/M3` but not `M2`) the immediate-parent version marks both nodes as root *and* both as leaf, and both cuts double-count. Finally, cut a single `target_type`'s total with `is_target_type_root`/`is_target_type_leaf` on the **fact**, not with the dim's flags: the dim's are computed over the union of all target types' nodes, and a campaign's HOUSEHOLD node set is usually a strict subset of its INDIVIDUAL one (218 of 302 projects in `table_dumps/project_target.csv` carry INDIVIDUAL only), so the union flag silently returns 0 for any type whose nodes exclude the union root.
- **Campaign/project context columns**: most silver entities repeat `project_id`, `project_type`, `project_type_id`, `project_name`, `campaign_number`, `campaign_id` as trailing "EXTRA FIELDS USED BY TRANSFORMER" — carry these through for any new entity so campaign-level rollups keep working.
- **ClickHouse table engine choice**: mart (`dm_*`) tables use plain `MergeTree` — they are rebuilt wholesale by their refreshable MV, so there is nothing to dedupe. Silver/dimension tables use `ReplacingMergeTree(<last_modified_or_created_time_column>)` so late-arriving updates from Kafka dedupe correctly; pick the column that reflects the entity's true last-write time (server `last_modified_time`/`created_time`, or client `client_last_modified_time` when the entity has separate client/server audit trails).
- **Campaign-specific fields live in child tables, not silver**: values that only some campaigns use (every `additionalFields` key, plus derived keys such as `cycleIndex`/`doseIndex`/`isVulnerable`, and project_task's beneficiary details: `age`/`gender`/`dateOfBirth`/`individualId` for individual projects, `householdId`/`memberCount` for household ones) go into `<entity>_campaign_field` (`05_silver_tables.sql`, right after the parent): one row per `(id, key)` with the value TYPED into exactly one of `value_string` / `value_number` (Float64) / `value_date` (Date32) / `value_bool` / `value_array` (Array(String)), named by `value_type`, the other four sent as NULL (`value_array`: `[]`, an Array can't be Nullable) so they take their DDL `DEFAULT` (`'NOT_APPLICABLE'`, `0`, `1970-01-01`, `false`, `[]`; relies on `insert_null_as_default`, pinned in `CLICKHOUSE_INSERT_SETTINGS`) so non-technical users never cast — typed per value by one generic rule in `campaign_field_rows_sql` (true/false → bool; any valid JSON array, or a string holding one → array, one text per element: strings unquoted, numbers/bools/objects as their JSON text; plain number without a leading zero, integers ≤ 15 digits → number; a real `YYYY-MM-DD` → date; everything else, incl. zero-padded text like `"03"`, datetime text, JSON objects and invalid `[` text → string; epoch-ms stays a number), so a key can carry different types on different rows. `ReplacingMergeTree(last_modified_time)` holding the parent's version value, `ORDER BY (id, key)` — one child table per entity, never a shared one. Exists for project_task, household, household_member (its own + individual keys only; household keys are in `household_campaign_field`), project_beneficiary and stock; written by those entities' DAGs in `sql_based_dags/`, and the ONLY place these values are stored: the silver tables carry no derived `additional_details` blob (household, household_member, project_beneficiary, stock), no task `cycleIndex`/`doseIndex`/`delivery_strategy`/`age`/`gender`/`date_of_birth` and no stock `facility_target` (dropped at cutover). The raw bronze blobs stay as silver columns (`household_additional_fields`, `member_additional_fields`, `beneficiary_additional_fields`, stock `additional_fields`, and project_task's `additional_details`, which is the raw `stg_project_task.additional_details`), as do task `individual_id`/`household_id`/`member_count`. To give an entity a child table, set `campaign_fields=campaign_field_rows_sql(<pairs helper>)` and `campaign_version_column` on its `SilverTarget`: the slice is then computed once into a session `TEMPORARY TABLE … ENGINE = Memory` and both the silver row and its child rows are inserted from it (no second pass over bronze, no materialized views). Keys are passed through generically, so a new `additionalDetails` key needs no code or DDL change. A key dropped by a later record version stays behind, so readers join on `child.last_modified_time = parent version`. Marts read these values from the child tables: `mv_dm_smc_administered_base`, `mv_dm_zero_dose_daily_by_node`, `mv_dm_missed_children_daily_by_node` (10) and `mv_dm_stock_facility_points` (11) pivot the child table (`anyIf(value_<type>, key = …)`, cast to the old silver type) joined on the parent's version; follow that pattern in any new mart that needs a campaign value. The custom report SQL in `custom_reports_reference/` still reads the dropped columns and has yet to be ported.
- **Indexing**: add `set(0)` data-skipping indexes on the boundary-code columns used for geographic filtering, and `minmax` indexes on date/timestamp columns queried by range (see `stock_entity`, `project_task_entity` for examples with multiple indexes).
- **Postgres vs. ClickHouse representation**: when adding a Postgres enriched-table counterpart to a ClickHouse silver table, keep nested/variable JSON fields as `JSONB` in Postgres even though the ClickHouse side flattens them into typed columns — do not flatten on the Postgres side unless a specific query pattern requires it.
- Column comments in the DDL (e.g. `-- Household.address (flattened)`) trace fields back to the source DIGIT service's domain object; preserve this traceability when adding columns for a new entity.
- **Bronze read window column**: a per-entity transformation DAG's bronze read (count + chunked/paginated read) must filter and keyset-paginate on the bronze table's own `_ingested_at` column, never on `last_modified_time`. `last_modified_time` reflects when a record changed at the *source* Postgres DB; because of pipeline latency (Debezium → Kafka → raw event store → the raw-to-bronze DAG), a row modified within a given `[start_time, end_time)` window can land in bronze well after that window has already been processed, so filtering on it would silently and permanently miss such late-arriving rows. `_ingested_at` correctly captures "what showed up in bronze during this run," independent of when the source-side edit happened. `last_modified_time` is still the right column for the silver-side `ReplacingMergeTree` versioning — that's a separate concern from this read-side window filter. See `project_task_transformation.py`'s `_count_bronze_records`/`_iter_bronze_chunks` for the reference implementation (keyset pagination on `(id, _ingested_at)` — id *first*, because a `DateTime64(3)` cursor value doesn't round-trip exactly through query parameters and `_ingested_at` alone isn't unique across a single ingestion flush; the docstring there has the infinite-loop reproduction). For `project` only (a pilot), that Step 1 window read is served by the narrow `prj_ingested_at` projection and the two join sides by `prj_by_project` projections — see `ClickHouse_ddl/14_bronze_projections.sql` and `BRONZE_READ_SCALABILITY.md` Option A′. Keep `project_transformation.py`'s Step 1 column list to `id, tenant_id, _ingested_at` with no `FINAL`, and extend a projection before reading a new column through it, or the projection silently becomes ineligible and the full scan returns.
- **No unconditional joins for mutually-exclusive per-row lookups**: when a row's next enrichment step branches on a value already known per row (e.g. a task's `beneficiaryType` is `HOUSEHOLD` *or* `INDIVIDUAL`, never both), don't `LEFT JOIN` every branch's target table onto the main multi-table bronze read — that makes ClickHouse do join work against every branch's table for every row, even though at most one branch could ever apply. Instead, extract+group the rows needing each branch (by tenant, mirroring the `extract_*_lookup_keys` shape from `egov_api_utils.py`), then run one small, targeted, lean query per branch (e.g. a 2-table join through the relevant bridge table only), and skip a branch's query entirely when no rows in the chunk need it. See `python_reference/project_task_transformation.py`'s `_extract_beneficiary_lookup_keys`/`_resolve_household_details`/`_resolve_individual_details` for the reference implementation (the SQL DAG does the same with slice-filtered join sides).
