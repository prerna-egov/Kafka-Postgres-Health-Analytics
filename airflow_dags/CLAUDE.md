## Repository layout

- `ClickHouse_ddl/` — DDL for the ClickHouse side of the pipeline (Kafka table engine, raw event store, bronze/silver tables, dimension tables).
- `ddl/` — DDL for the downstream analytics Postgres side (enriched/transformed tables consumed by reporting, and data marts).
- `airflow_dags/` — Airflow DAGs orchestrating movement of data between the ClickHouse stages.

## Data architecture (Postgres CDC → Kafka → ClickHouse → Postgres analytics)

This pipeline captures change-data-capture (CDC) events from the operational Postgres database behind eGov DIGIT Health Campaign Management (HCM) services and makes them analytics-ready for reporting. The core domain entities are household, household member, project, project task, project beneficiary, project staff, PGR complaints, attendance (log/register), and stock/stock reconciliation. The flow is:

1. **Source Postgres (operational DB, outside this repo)** — the live DIGIT service database that HCM applications write to.
2. **Debezium** — captures write-ahead log changes from the source Postgres tables and publishes them as change events to Kafka topics (one topic per source table/entity, e.g. `save-household-events`).
3. **Kafka table engine (`ClickHouse_ddl/01_kafka_event_consumers.sql`)** — ClickHouse `Kafka` engine tables consume each topic and store each message as a raw JSON string. These are not queried directly; they only exist to bridge Kafka into ClickHouse.
4. **Materialized view → raw event store (`ClickHouse_ddl/02_raw_events_store.sql`)** — a materialized view runs on top of each Kafka engine table and inserts into a raw event store table, giving a persisted, replayable log of every CDC event. Currently an empty placeholder.
5. **Bronze tables (`ClickHouse_ddl/03_bronze_tables.sql`)** — intended to be populated by an Airflow DAG that reads from the raw event store and writes into bronze tables, which are structural replicas of the source Postgres tables (`stg_<entity>`, pre-transformation, one-to-one with the operational schema, plus an `_ingested_at` arrival-time column). The table definitions themselves already exist; the raw-event-store-to-bronze *loading* DAG does not (see step 9) — today, bronze data is assumed to already be present when a `<entity>_transformation.py` DAG runs.
6. **Silver tables (`ClickHouse_ddl/04_silver_tables.sql`)** — populated by the per-entity transformation DAGs that `bronze-to-silver_orcestrator.py` triggers (see below), which read from bronze, apply transformations (flattening nested fields, joining in boundary hierarchy and campaign/project context, etc.), and write fully flattened, analytics-ready tables per entity (`household_entity`, `household_member_entity`, `project_beneficiary_entity`, `pgr_complaints_entity`, `project_staff_entity`, `stock_entity`, `service_task_entity`, `stock_reconciliation_entity`, `project_entity`, `project_task_entity`). All use `ReplacingMergeTree` keyed on a modification timestamp column (dedup-on-merge semantics), `ORDER BY` tuples starting with tenant/campaign identifiers for query locality, and secondary `set()`/`minmax` data-skipping indexes on geography and date columns for fast filtering at scale. `project_task_transformation.py`, `project_transformation.py`, `project_staff_transformation.py`, `project_beneficiary_transformation.py`, `household_transformation.py`, `household_member_transformation.py`, `stock_transformation.py`, `pgr_transformation.py`, `stock_reconciliation_transformation.py`, `attendance_staff_transformation.py`, `attendance_register_transformation.py`, `attendee_transformation.py`, `attendance_log_transformation.py`, `bill_transformation.py`, `bill_detail_transformation.py`, `referral_transformation.py`, `side_effect_transformation.py`, `hf_referral_transformation.py`, `user_action_transformation.py`, `service_task_transformation.py`, and `muster_roll_transformation.py` are the twenty-one entities with real transform logic today: each reads bronze, joins in related bronze tables, enriches rows with boundary/user/product/individual/facility data as applicable (see [Shared helper modules](#shared-helper-modules)), and writes chunk-by-chunk into its silver table (`project_task_entity`, `project_entity`, `project_staff_entity`, `project_beneficiary_entity`, `household_entity`, `household_member_entity`, `stock_entity`, `pgr_complaints_entity`, `stock_reconciliation_entity`, `attendance_staff_entity`, `attendance_register_entity`, `attendee_entity`, `attendance_log_entity`, `bill_entity`, `bill_detail_entity`, `referral_entity`, `side_effect_entity`, `hf_referral_entity`, `user_action_entity`, `service_task_entity`, `muster_roll_entity` respectively).
7. **Dimension tables (`ClickHouse_ddl/05_dimension_tables.sql`)** — supporting dimensions, e.g. `boundary_hierarchy_dim`, which unfurls a hierarchical boundary definition (country → region → district → facility → settlement, encoded as `level_one_code` … `level_nine_code` elsewhere) into one row per level.
8. **Downstream analytics Postgres (`ddl/01_transformed_data_tables.sql`, `ddl/02_data_marts.sql`)** — a separate, reporting-facing Postgres database (distinct from the source operational Postgres in step 1) holding enriched tables (`household_enriched`, `household_member_enriched`, `project_beneficiary_enriched`, `attendance_log_enriched`, `attendance_register_enriched`, `pgr_complaints_enriched`) and data marts. These favor `JSONB` for nested/variable structures (`additional_details`, `boundary_hierarchy`, etc.) where the ClickHouse silver tables instead flatten the same data into typed columns — keep this asymmetry in mind when writing transformation logic between the two. `02_data_marts.sql` is an empty placeholder; how silver data reaches this Postgres is not yet defined in this repo — do not assume a mechanism, ask if it's unclear.
9. **Orchestration (`airflow_dags/dags/`)** — Airflow DAGs drive steps 5 and 6 (raw → bronze, and bronze → silver). Only the bronze→silver side exists so far; the raw→bronze DAG does not exist yet.

## Orchestrator DAG and per-entity transformation DAGs

`bronze-to-silver_orcestrator.py` (`dag_id=bronze_to_silver_orchestrator`) does not itself do any bronze→silver work. Each entity gets its own DAG file (`<entity>_transformation.py`, `dag_id=<entity>_transformation`, e.g. `project_task_transformation.py`) so that transformation logic for one entity can change without touching the others. The orchestrator, on each scheduled run:

1. Computes a time window from its own `data_interval_start`/`data_interval_end`.
2. Reads the ordered list of entities to process from the `entity_transformation_order` Airflow Variable.
3. For each entity in order, triggers `<entity>_transformation` with `conf={"start_time": ..., "end_time": ...}` and waits for it to finish before triggering the next one. If an entity's DAG file doesn't exist yet, it's skipped (not a hard failure) and the chain continues; a genuine failure in a triggered DAG halts the chain.

Both the entity order and the orchestrator's own schedule cadence are controlled by Airflow Variables rather than hardcoded, so operators can change them without a code deploy — see [`airflow_dags/README.md`](README.md) for exactly how to set them and what values are valid. When adding a new entity, follow the `project_task_transformation.py` pattern (TaskFlow API DAG, `schedule=None`, reads `start_time`/`end_time` from `dag_run.conf`) rather than inventing a new structure, and add its key to `entity_transformation_order` once it's ready to run.

## Shared helper modules

Two plain (non-DAG) helper modules live alongside the DAG files in `airflow_dags/dags/` and are meant to be reused by every future `<entity>_transformation.py`, not just `project_task_transformation.py`:

- **`clickhouse_utils.py`** — `get_clickhouse_client()`, building a `clickhouse-connect` client from the `clickhouse_default` Airflow Connection (see [README](README.md#connecting-entity-dags-to-clickhouse)).
- **`egov_api_utils.py`** — calls to external eGov DIGIT services (boundary-service, user-service, MDMS), each following the same simplified-vs-Java approach: read the reference Java `transformer` service (in the sibling `health-campaign-services` repo) to understand the real request/response shape, then reimplement only what's actually needed, dropping incidental complexity the Java code carries (MDMS-based display-name/label resolution, localization-service calls) when the same data is already available more directly (e.g. a boundary code's ancestor path is fetched directly via the boundary-service's `codes=` filter, not derived from an MDMS-labeled whole-tree walk; a project's `beneficiaryType` is read straight out of its own `additional_details` JSON instead of an MDMS `PROJECT_TYPES`-master lookup). Every external call degrades gracefully — wrapped in try/except, logs and returns an empty/default result on any failure, never a hard chunk failure. It also hosts an **entity-agnostic three-stage pattern** (`extract_*_lookup_keys` → `resolve_*` → `attach_*`) for enriching a chunk of rows from an external source: an entity file supplies a small `get_key(row)` function mapping its own column names to a generic lookup key, and the reusable functions handle grouping/deduping, batched resolution, and merging results back onto rows. Follow this pattern (rather than inventing a new one) when a new entity needs boundary/user enrichment, or needs a similar kind of external/lookup-table enrichment of its own.

## Conventions to follow when extending the schema

- **Boundary hierarchy flattening**: entities that are geography-aware repeat the same `level_one_code` … `level_nine_code` + `hierarchy_type` column block (see any table in `04_silver_tables.sql`). Match this exact naming/ordering when adding new entities rather than inventing a new representation.
- **Campaign/project context columns**: most silver entities repeat `project_id`, `project_type`, `project_type_id`, `project_name`, `campaign_number`, `campaign_id` as trailing "EXTRA FIELDS USED BY TRANSFORMER" — carry these through for any new entity so campaign-level rollups keep working.
- **ClickHouse table engine choice**: silver/dimension tables use `ReplacingMergeTree(<last_modified_or_created_time_column>)` so late-arriving updates from Kafka dedupe correctly; pick the column that reflects the entity's true last-write time (server `last_modified_time`/`created_time`, or client `client_last_modified_time` when the entity has separate client/server audit trails).
- **Indexing**: add `set(0)` data-skipping indexes on the boundary-code columns used for geographic filtering, and `minmax` indexes on date/timestamp columns queried by range (see `stock_entity`, `project_task_entity` for examples with multiple indexes).
- **Postgres vs. ClickHouse representation**: when adding a Postgres enriched-table counterpart to a ClickHouse silver table, keep nested/variable JSON fields as `JSONB` in Postgres even though the ClickHouse side flattens them into typed columns — do not flatten on the Postgres side unless a specific query pattern requires it.
- Column comments in the DDL (e.g. `-- Household.address (flattened)`) trace fields back to the source DIGIT service's domain object; preserve this traceability when adding columns for a new entity.
- **Bronze read window column**: a per-entity transformation DAG's bronze read (count + chunked/paginated read) must filter and keyset-paginate on the bronze table's own `_ingested_at` column, never on `last_modified_time`. `last_modified_time` reflects when a record changed at the *source* Postgres DB; because of pipeline latency (Debezium → Kafka → raw event store → the raw-to-bronze DAG), a row modified within a given `[start_time, end_time)` window can land in bronze well after that window has already been processed, so filtering on it would silently and permanently miss such late-arriving rows. `_ingested_at` correctly captures "what showed up in bronze during this run," independent of when the source-side edit happened. `last_modified_time` is still the right column for the silver-side `ReplacingMergeTree` versioning — that's a separate concern from this read-side window filter. See `project_task_transformation.py`'s `_count_bronze_records`/`_iter_bronze_chunks` for the reference implementation (keyset pagination on `(_ingested_at, id)`, since bronze has no monotonic integer/sequence column and `_ingested_at` alone isn't unique across a single ingestion flush).
- **No unconditional joins for mutually-exclusive per-row lookups**: when a row's next enrichment step branches on a value already known per row (e.g. a task's `beneficiaryType` is `HOUSEHOLD` *or* `INDIVIDUAL`, never both), don't `LEFT JOIN` every branch's target table onto the main multi-table bronze read — that makes ClickHouse do join work against every branch's table for every row, even though at most one branch could ever apply. Instead, extract+group the rows needing each branch (by tenant, mirroring the `extract_*_lookup_keys` shape from `egov_api_utils.py`), then run one small, targeted, lean query per branch (e.g. a 2-table join through the relevant bridge table only), and skip a branch's query entirely when no rows in the chunk need it. See `project_task_transformation.py`'s `_extract_beneficiary_lookup_keys`/`_resolve_household_details`/`_resolve_individual_details` for the reference implementation.
